## 已解决的整合问题

### 1. 保留上游 direct steer 旧任务收尾

原多模分支与上游 `#81` 同时调整 `src/dispatch/bot.ts`，存在文本冲突。整合后保留两部分行为：

- 同模型、同图片能力的普通文本追问继续 direct steer；成功后向旧设备任务发送空的 final 帧，随后登记新任务，保留上游 `#81` 的处理。
- 原生图片、模型/图片能力变化及已经排队的后续消息，进入完整新轮次，避免图片被纯文本 steer 丢弃。
- 旧任务收尾、模型持久化更新和本轮能力准入分别遵循原有身份与时序约束。

### 2. 保留团队 11.7.9.310 版本边界

没有把原分支的 `11.7.9.301` 阈值带回团队代码。

新增测试验证 300、301、309、310、311 版本的工具可见性；使用真实主链路和 legacy formatter 验证 301/309 的旧端帧以及 310 的新端帧。

### 3. 收窄严格等待，保护普通旧请求

原实现中，完整派发只要有 `modelName` 就进入新的 30 秒严格检查。本次收窄为：需要强制新轮次，或者本轮有合法能力声明的明确模型选择。

没有能力声明、也没有强制新轮次要求的普通旧文本请求，保留团队原有三秒文本回退行为。增加了携带 `modelName` 的旧请求回归用例。

### 4. 收窄模型降级保护，保护其他 Provider 使用者

图片降级保护仅用于本轮声明支持原生图片、且上下文包含图片的 Channel 请求。

旧文本请求及没有 Channel 能力上下文的调用，保留原来的 Kimi 降级策略；未将图片能力过滤或新降级规则全局应用到定时任务和其他调用方。

### 5. 保留上游 #83 的 70 秒等待上限

PR 创建后，团队新增 `9ea15f5`（#83），与多模派发入口形成内容冲突。整合后完整保留上游 `waitForPreviousTurnWithTimeoutWarning`：steer 回退等待上一轮最多 70 秒，超时记录日志并进入后续处理。

普通文本回退保留上游行为；原生图片或需要严格准入的新轮次，在该等待之后仍检查 SDK 是否空闲，最多额外等待 30 秒。SDK 仍忙时明确拒绝当前请求并保留旧任务，SDK 空闲时完整传递图片。该时限不等于整个排队或模型执行的总时限。

保留上游新增的 70 秒回归测试，并新增 SDK 忙/空闲两个原生图片组合用例。

## 有意改变的行为

以下是需求功能本身的变化，不能描述为所有行为与旧版完全一致：

- 本轮 `modelInput` 包含 `image` 时，主模型直接收到图片，隐藏 `image_reading`，关闭本轮通用前置识图。
- 缺失或非法字段时，本轮按文本模式处理，不继承上一轮图片能力。
- 原生图片或模型/能力变化可能需要排队；严格准入失败时会返回明确错误。
- 原生图片增加内容解码与大小校验，坏图或部分下载失败时整条请求失败。
- 同名附件使用独立本地文件名，媒体类型数组保持位置对应。
- 独立日志修复会改变 MemoryFileRead 的日志内容，但不会改变 A2A 发送正文。

## PR 评审与联调重点

1. 重点评审共享入口 `bot.ts`、`monitor.ts` 与 Provider 的生效范围。
2. 确认本轮模型名及能力来自同一份端侧声明，尤其多端切换模型的场景。
3. 联调流式处理中追加图片、随后发送文本、取消和清空上下文，观察任务卡及终态。
4. 验证网关支持 SDK 生成的 data URL，以及实际多图数量、格式与总包限制。
5. 核对部署图片处理器和识图 Skill，原生模式不能再强制重复调用图片理解工具。

本地 HTTP 测试使用真实 SDK 序列化和模拟传输，尚未替代上述真实环境联调。
